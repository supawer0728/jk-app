# 다중선택 삭제만 `common`으로 공통화하고, '전체 삭제'는 각 화면 고유로 남긴다

**상태**: 결정됨
**날짜**: 2026-07-18

## 맥락

이슈 #88은 자식 TODO와 함께 "다중선택 삭제 공통화"를 다룬다. 목록형 화면 여럿(TODO,
투자종목, 벤치마크)이 항목을 여러 개 골라 한 번에 지우는 UX를 필요로 하는데, 각 화면이 선택
모드 상태(선택 여부·선택된 id 집합·진입/토글/종료)를 제각각 구현하면 중복이 생긴다.

한편 투자종목·벤치마크 화면에는 '전체 삭제'(그 명의/카테고리의 항목을 모두 지움)라는 별도
동작도 있다. 공통화 범위를 어디까지로 할지 정해야 했다.

## 결정

- 선택 모드 상태 홀더 `com.jkapp.common.MultiDeleteState<T>`와 하단 바 `MultiDeleteBar`로
  **'선택 삭제'만 공통화**한다. TODO·투자종목·벤치마크 세 화면이 공유한다.
- 투자종목·벤치마크의 **'전체 삭제'는 각 화면 고유 동작으로 남긴다.** 공통 컴포넌트에 넣지 않는다.
- `MultiDeleteState<T>`는 id 타입을 제네릭으로 받아(String, Pair 등 화면별로 다름) 화면별 식별자
  형태를 그대로 수용한다.

## 근거

- **공통된 것만 공통화**: 세 화면의 진짜 공통 관심사는 "선택 모드 상태 관리 + 선택 삭제 실행"이다.
  이 부분만 추출하면 중복이 사라지면서 화면 고유 로직은 건드리지 않는다.
- **'전체 삭제'는 도메인 의미가 다르다**: 전체 삭제 대상 범위(어떤 명의·카테고리를 전부 지울지)는
  투자종목·벤치마크 각자의 도메인에 종속된다. TODO에는 대응 개념이 없다. 세 화면에 공통 API로 강제
  주입하면 인터페이스에 특정 화면에서만 의미 있는 파라미터가 새어 들어와 god interface로 번진다.
- **제네릭 id**: 화면마다 항목 식별자 형태가 달라(TODO는 문서 id, 투자종목/벤치마크는 복합 키)
  타입을 고정하면 재사용이 막힌다. 제네릭으로 두면 상태 관리 로직만 공유하고 식별자는 각자 정한다.

## 검토한 대안

- **전체 삭제까지 공통 바에 포함**: 공통 컴포넌트가 특정 화면에만 있는 '전체 삭제' 개념을 알아야
  하고, TODO에는 불필요한 버튼/콜백이 생긴다. 공통화가 오히려 결합을 늘려 제외.
- **각 화면이 선택 모드를 개별 구현(공통화 안 함)**: 이슈가 요구한 중복 제거를 달성하지 못한다. 제외.
- **id 타입을 String으로 고정**: 복합 키를 쓰는 화면에서 문자열 인코딩/디코딩이 강제돼 사용처가
  지저분해진다. 제네릭이 더 단순해 제외.

## 예상 결과

- `com.jkapp.common.MultiDeleteState`/`MultiDeleteBar`가 신설되고 TODO·투자종목·벤치마크가 이를
  사용한다. 현재-사실은 `doc/dev/infra/common.md`와 각 finance FEATURE 문서에 반영한다.
- '전체 삭제'는 투자종목·벤치마크 화면에 그대로 남아 각 화면이 자신의 삭제 범위를 정의한다.
- 새 목록형 화면이 다중선택 삭제를 필요로 하면 `MultiDeleteState<T>` 재사용으로 대응한다.

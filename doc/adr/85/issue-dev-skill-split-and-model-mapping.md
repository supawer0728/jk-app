# issue-dev 스킬을 Phase별 하위 스킬로 분리하고 오케스트레이터가 model을 매핑해 위임한다

**상태**: 결정됨
**날짜**: 2026-07-11

## 맥락

`issue-dev` 스킬(`.claude/skills/issue-dev/SKILL.md`)은 GitHub 이슈 하나를 받아 워크트리 생성부터
Draft PR까지 전체 개발 사이클(Phase 1~5)을 수행한다. 이 전체 절차가 단일 SKILL.md(약 194줄)에
담겨 있어 다음 문제가 있었다(이슈 #85).

- **단계별 model 최적화 불가**: 이슈 조회·커밋 같은 기계적 단계와 요구사항 분석·리뷰 같은
  추론 집약적 단계가 하나의 model로 실행된다. 쉬운 단계에 과한 model을 쓰거나, 어려운 단계에
  부족한 model을 쓰게 된다.
- **재사용·단독 실행 불가**: "요구사항 분석만" 또는 "PR 작성만" 같은 개별 단계를 따로 실행할 수 없다.
- **관심사 혼재**: 단일 문서라 각 단계의 책임 경계가 흐리다.

이슈 #85에서 각 Phase를 독립 하위 스킬로 분리하고, `issue-dev`를 이들을 조합하는 오케스트레이터로
재구성하며, 단계별로 적정 model을 적용한다.

## 결정

### 1. Phase 1~5를 5개 하위 스킬로 분리한다

| 하위 스킬 | Phase | 책임 |
|-----------|-------|------|
| `issue-dev-fetch` | 1 | 이슈 조회 + slug 생성 |
| `issue-dev-analyze` | 2 | 요구사항(AC/제약) 추출 + 영향 문서 모순 검증 |
| `issue-dev-implement` | 3 | 문서 우선 반영 → 코드 → 테스트 (구현 루프) |
| `issue-dev-decide` | 4 | 의사결정 분류 + ADR 초안 |
| `issue-dev-pr` | 5 | 정합성 최종 검증 + 커밋/push + Draft PR |

각 하위 스킬 SKILL.md는 해당 단계의 **단일 진실(SSOT)**이며, 단독으로도 실행 가능하다.

### 2. `issue-dev`는 오케스트레이터로서 하위 스킬을 순차 위임한다

- 오케스트레이터는 각 단계를 **`Agent` 도구(subagent)**로 실행하되, `model`을 단계별로 오버라이드한다.
- subagent에게는 "`.claude/skills/issue-dev-<phase>/SKILL.md`를 읽고 이슈 #N에 대해 실행하라"는
  지시와 **단계 간 상태**만 전달한다(지침 본문은 인라인하지 않는다 → 중복 제거, DRY).
- subagent는 구조화된 결과를 오케스트레이터에 반환한다.

### 3. 단계별 model 매핑 (작업 난도 기반)

| 하위 스킬 | model | 근거 |
|-----------|-------|------|
| `issue-dev-fetch` | Haiku | 조회·문자열 가공 등 기계적 |
| `issue-dev-analyze` | Opus | AC 추출·문서 모순 판단은 추론 집약 |
| `issue-dev-implement` | Sonnet | 코드/문서 편집 등 실행 중심 |
| ↳ Phase 3-5 코드·문서 리뷰 | Opus | 결함·정합성 판단은 추론 집약. 오케스트레이터가 별도 위임 |
| `issue-dev-decide` | Opus | 아키텍처·데이터·보안 결정 판단 |
| `issue-dev-pr` | Haiku | 커밋·push·PR 생성 등 기계적 |

### 4. 세션 상태 전환·사용자 상호작용·최종 승인은 오케스트레이터가 보유한다

다음 작업은 subagent가 수행하면 의도대로 동작하지 않으므로 **오케스트레이터만** 수행한다.

- **`EnterWorktree` / `ExitWorktree`**: 세션의 작업 디렉터리를 바꾼다. subagent가 호출하면
  부모 세션(오케스트레이터)이 워크트리로 이동하지 않으므로 이후 단계가 격리 트리에서 동작하지 않는다.
- **`AskUserQuestion`**: 사용자 상호작용. subagent는 자율 실행되어 사용자에게 직접 질문할 수 없다.
- **`TaskCreate`/`TaskUpdate`**: 세션 단위 할 일 목록.
- **최종 승인**(작업 범위 확인, 중요 의사결정 승인, PR 생성 승인).

따라서 하위 스킬 subagent는 **분석·구현·기계적 작업과 그 결과 반환**을 맡고, 상호작용이 필요한
지점은 "열린 질문/필요 결정" 목록으로 반환해 오케스트레이터가 처리한다.

### 5. 중첩 subagent를 피한다

subagent 안에서 다시 subagent를 띄우지 않는다. Phase 3-5 리뷰(Opus)는 구현 subagent(Sonnet)가
내부에서 띄우지 않고, **오케스트레이터가 구현↔리뷰 루프를 직접 돌리며** 리뷰를 별도 Opus로 위임한다.
(단독 실행 시에는 `issue-dev-implement`가 리뷰를 인라인으로 수행할 수 있다.)

## 근거

- **model 매핑**: 기계적 단계를 Haiku로 낮추고 추론 단계만 Opus로 올려, 품질 저하 없이 비용을
  줄인다. Sonnet은 편집 처리량이 좋아 구현 단계에 적합하다.
- **SSOT 위임(subagent가 SKILL.md를 읽음)**: 지침을 오케스트레이터에 인라인하면 하위 스킬과
  이중 관리가 되어 표류(drift) 위험이 크다. 하위 스킬을 읽게 하면 한 곳만 고치면 된다.
- **오케스트레이터가 세션/상호작용 보유**: Claude Code 도구의 실제 동작(subagent의 cwd 고정,
  자율 실행)에서 강제되는 제약이다. 선택이 아니라 올바른 동작을 위한 필요조건이다.
- **하위 호환**: 오케스트레이터의 입력(`/issue-dev <번호>`)과 최종 결과(Draft PR)는 그대로다.
  내부 실행 구조만 바뀐다.

## 검토한 대안

- **하위 스킬 frontmatter의 `model`에만 의존**: `Skill` 도구로 하위 스킬을 부르면 메인 대화에서
  실행되어 실제 model 전환 보장이 불확실하다. frontmatter `model`은 단독 실행 시의 의도 표기로만
  두고, 실제 단계별 model은 오케스트레이터의 `Agent` 오버라이드로 강제한다.
- **오케스트레이터가 각 Phase 지침을 인라인**: 하위 스킬과 지침이 두 곳으로 갈라져 중복·표류가
  생긴다. SSOT 위임으로 배제.
- **분리하지 않고 단일 스킬 유지 + model만 조정**: 단일 스킬은 전체가 한 model로 돌아 단계별
  최적화가 불가능하고, 단독 실행·재사용 요구를 만족하지 못한다.
- **기능 응집 기준으로 3~4개로 묶기**: Phase 경계가 이미 명확하고 기존 구조와 1:1 대응해
  추적성이 높으므로 5개 분리를 택했다.

## 예상 결과

- `.claude/skills/`에 `issue-dev-fetch/analyze/implement/decide/pr` 5개 하위 스킬이 추가되고,
  `issue-dev`는 오케스트레이터로 축소·재작성된다.
- 각 단계가 매핑된 model로 실행되어 비용/품질 균형이 개선된다.
- 각 하위 스킬을 단독 실행할 수 있다.
- docs as code 3원칙(변경 전 문서 반영·모순 검증·PR 전 정합성)은 하위 스킬과 오케스트레이터
  양쪽에 유지된다.
- 워크트리는 파일시스템을 공유하므로 subagent의 파일 편집은 그대로 반영된다. 단계 간 상태는
  이슈 번호·slug·브랜치·워크트리 경로 등 최소 정보만 오케스트레이터가 전달한다.

## 후속 과제 (이번 범위 밖)

- 하위 스킬의 구조화 반환값을 스키마로 엄격화(예: JSON 계약)하는 것은 필요 시 별도로 다룬다.
- 여러 이슈를 병렬 오케스트레이션하는 상위 워크플로우는 이번 범위에 포함하지 않는다.
